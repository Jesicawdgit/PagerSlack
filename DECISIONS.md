# Decisions

## Phase 0 — Skeleton

- **No early deploy.** CLAUDE.md's original Phase 0 included a trivial Render/Vercel deploy as "cheap insurance." User explicitly deferred all deployment (including account creation, not yet done) to the Phase 10 cutover, to avoid debugging deploy and application logic simultaneously. Everything through Phase 9 is verified locally.
- **API mount prefix is `/api/v1`**, not the un-prefixed paths implied by CLAUDE.md's endpoint list. CLAUDE.md's Vercel env var example (`VITE_API_URL=<render backend URL>/api/v1`) is explicit, so all routes mount under `/api/v1` to match. Phase 0's health route is `GET /api/v1/health`.
- **Vite dev proxy** (`/api` → `http://localhost:5000`) used for local convenience so the frontend can call relative paths and avoid CORS/cookie friction in dev. The built/deployed frontend won't have this proxy — real CORS + cookies in `app.js` are still exercised at the Phase 10 cutover.
- **No npm workspaces.** `backend/` and `frontend/` already have independently-installed `node_modules` on very new major versions (express@5, mongoose@9, react@19). Converting to workspaces now risks dependency-resolution churn for no Phase 0 benefit. Two terminals for two dev servers is fine for this project's size.
- **No refresh-token rotation** in this MVP (see CLAUDE.md's auth section) — out of scope for Phase 0, noted here as a placeholder since this file is where that tradeoff will be documented once auth lands in Phase 1.

## Phase 1 — Auth

- **No refresh-token rotation** (confirmed, see Phase 0 placeholder above). JWT cookie is valid for 7 days with no server-side revocation list; logout only clears the client's cookie. Acceptable for an MVP demo, documented here as the tradeoff CLAUDE.md's auth section calls out.
- **`team` field deferred to Phase 2.** Nothing for a `User.team` ref to point to until the `Team` model exists — adding it now would be a dead field, not an oversight.
- **JWT expiry and cookie `maxAge` hardcoded (`7d`)**, not a 6th env var. `environment.js` only validates what the app truly can't boot without; token lifetime is an MVP-tuning value, not a boot-blocking one.
- **Local cookie-auth verification is proxy-assisted.** Vite's dev proxy makes requests same-origin from the browser's perspective, so passing all Phase 1 checks locally does not exercise the real cross-origin `sameSite:'none'` cookie flow — that only gets tested for real at the Phase 10 deploy cutover.
- **Bootstrap 5 (CSS only) added as a dependency**, deviating from the original "plain CSS, no framework" tech stack line — driven by explicit user-supplied mockups and a whole-app color palette (not just this phase). No `react-bootstrap`, no Bootstrap JS. `CLAUDE.md`'s "Tech stack" line updated to match.
- **Swagger docs centralized in `config/swagger.js`** rather than inline JSDoc comments scattered across each route file — a single file holds every `@swagger` annotation block, still written alongside each route's slice (not deferred), just organized in one place instead of per-route-file.
- **Removed the stray dark-mode `prefers-color-scheme` block from `index.css`** (a Phase 0 leftover from the stock Vite template) — it silently overrode the new deliberate off-white palette on dark-mode systems, and CLAUDE.md puts dark/light theming out of scope entirely.
- **`Button`/`Badge` reusable components built now** (not deferred to their "second consumer"), per explicit user request to keep styling centralized from the start. `Modal` stays deferred — no consumer until Phase 4's `CreateIncidentModal`.

## Phase 2 — Teams & Channels

- **`User.team` is the single source of truth for membership** — one nullable `ObjectId ref Team`, no `Team.members` array. Two collections both tracking the same relationship would need to stay in sync; one ref avoids that entirely.
- **No join/invite endpoint** — not in CLAUDE.md's ~23-endpoint list. `POST /teams` auto-assigns the creator to the team they create; that's the only way `user.team` gets set via the API (the Phase 9 seed script sets it directly on the 3 demo users, bypassing the API).
- **`ALREADY_ON_TEAM` (409)** guards `POST /teams` — without it, a user with a team could silently orphan it by creating a second one, with no join endpoint to get back. Cheap, protects data integrity the auto-assign design itself creates.
- **No membership enforcement on reads or channel-creation writes** — any authenticated user can `GET` any team's channels or `POST` a channel into any team. Matches "no private channels" being explicitly out of scope; untestable anyway with 1–2 teams ever existing in this demo. Deliberate, not an oversight.
- **`teamService.js`/`channelService.js` built despite CLAUDE.md's folder tree omitting them** — the non-negotiable "controllers stay thin, business logic lives in services/" has no phase exception; the tree is read as an incomplete listing, following the `authService.js` precedent from Phase 1.
- **Flat route-file split**, not `mergeParams` nesting — `GET/POST /teams/:teamId/channels` live in `teamRoutes.js` (importing `channelController`); `channelRoutes.js` stays scoped to `GET /:id`. One route file owns one URL prefix, matching `authRoutes.js`.
- **`router.use(protect)` once at the top of `teamRoutes.js`**, not repeated per route — every route in that file needs auth, so gating the whole router is equivalent and shorter than five individual `protect` references.
- **`Topbar.jsx` deferred** — same precedent as Phase 1's `Modal.jsx` deferral. Nothing in the mockup or roadmap needs a distinct top bar yet.
- **`Workspace.jsx` repurposed, not deleted** — now the index route inside `AppLayout`: a create-team prompt for a teamless user, a "select a channel" empty state otherwise. Its old user-info/logout block relocated to `Sidebar.jsx`'s footer.
- **`param('id')`/`param('teamId')` validated with `.isMongoId()`** — first route-param validation in the project (Phase 1 had none). Without it a malformed id reaches Mongoose as a raw string and throws an uncaught `CastError` → generic 500 instead of a clean 400.
- **`Channel` has a compound unique index `{team:1,name:1}`**, same defense-in-depth pattern as `User.email` — an explicit `findOne` pre-check in `channelService` is the real guard; the index is the backstop.
- **Sidebar's active-channel highlight uses React Router's `NavLink` `isActive` render-prop** rather than manually comparing `useParams().channelId` against each channel — idiomatic, fewer lines, same result.
- **`AppLayout` has no `loading` state for its team/channels fetch.** Originally added, then removed — a newer `eslint-plugin-react-hooks` rule (`react-hooks/set-state-in-effect`) flags any `setState` call that's a synchronous top-level statement in an effect body (only tolerates `setState` inside a `.then`/`.catch` callback). Threading a `loading` flag through that constraint added real complexity for a Phase 8-tier ("empty/loading states") polish concern this phase doesn't need — channels simply render as they arrive.
- **`AuthContext`'s mount-time session-restore effect duplicates `refreshUser()`'s three lines instead of calling it.** Same ESLint rule as above: calling a component-scope function that itself calls `setState` (even asynchronously) from inside `useEffect` gets flagged, but the exact same logic written inline as a `.then/.catch/.finally` chain does not. `refreshUser()` still exists and is exported for `Workspace.jsx`'s post-create-team sync — this is a real, deliberate small duplication forced by the linter, not an inconsistency.

## Phase 3 — Messaging + Socket.IO core

- **Built in 4 sub-slices (A: socket plumbing, B: message persistence, C: realtime delivery, D: mentions/notifications), each paused for manual review** — an explicit user request given this is the first phase touching WebSockets. Each sub-slice had its own checkpoint verified live (browser DevTools handshake inspection, two-browser room-scoping test, cross-user mention delivery) before the next began.
- **Socket auth reuses `cookie-parser` via `io.engine.use(cookieParser())`** (Socket.IO 4.6+ feature, already on 4.8.3) rather than hand-rolling a parser or adding a new dependency — populates `socket.request.cookies.token` exactly like Express's `req.cookies.token`, so the socket auth middleware mirrors `authMiddleware.protect`'s logic almost line for line.
- **Two room types only, `user:<id>` and `channel:<id>`, no global broadcast** except the future `service:health_changed` (Phase 6) — every emit in `messageService.js`/`notificationEvents.js` is scoped `getIO().to(room).emit(...)`, checked deliberately during each file review since a one-character mistake here is the easiest way to violate this non-negotiable rule.
- **No channel-membership enforcement on `channel:join`** — consistent with Phase 2's "no membership enforcement on reads" decision; gating sockets more tightly than the REST API for the same data would be an inconsistency, not real hardening, given there's no private-channels feature to enforce in the first place.
- **`message:new` is the sole source of truth for the message list** — `Channel.jsx`'s send handler does not optimistically append the POST response locally. The sender is themselves a member of `channel:<id>` and receives their own broadcast, so appending from both the response and the socket event would duplicate the sender's own messages.
- **Channel room rejoin on the socket's `'connect'` event, not just on mount** — a reconnect gets a new `socket.id` and loses prior room memberships. `user:<id>` doesn't need this because the server rejoins it automatically in its own `connection` handler on every reconnect; `channel:<id>` isn't server-managed that way, so the client re-emits `channel:join` itself. Verified live by restarting the backend dev server mid-session.
- **`messageRoutes.js` kept as its own file with `express.Router({mergeParams:true})`**, unlike Phase 2's flat team/channel route file — CLAUDE.md's folder tree explicitly lists `messageRoutes.js` standalone this time, unlike the channels-under-teams case.
- **Skipped duplicating `param('id').isMongoId()` + `validateRequest` at the `channelRoutes.js` mount point.** The original sub-slice plan called for validating `id` both at the mount and again inside `messageRoutes.js` itself; since `messageRoutes.js` already validates `id` and applies `protect` internally, adding the same two checks at the mount would run them twice per request for no behavioral difference. Functionally identical, less code — a deliberate, flagged deviation from the written plan.
- **Mention matching**: regex `/@(\w+)/g` against message content, matched case-insensitively against the **first word** of each team member's `name` (no username/handle field exists, no members-list endpoint is in scope). Deduped via a `Set`, author excluded. Known, documented limitation: two team members sharing a first name both get notified — not fixed, since there's no username field to disambiguate with in scope.
- **`Notification` documents are persisted with no read/list API endpoint, ever.** "No notification center UI" (CLAUDE.md's exclusion list) is read as excluding the read/browse surface specifically, not the write/persistence layer — the only way a client learns of one is the live `notification:new` socket event. Mid-phase, the user proposed adding a notification page; declined and left unbuilt, since CLAUDE.md calls out "a notification center" twice, once under "cut immediately, no discussion." The persisted data means this remains cheap to add later if genuine spare time exists after Phase 10.
- **`Toast.jsx` built now, not deferred like `Modal.jsx` was** — two concrete named future consumers already existed (this phase's mentions, Phase 7's escalations), unlike `Modal.jsx`'s single speculative consumer at the time. Purely presentational; the toast queue/subscription state lives in `AppLayout.jsx`, not a new `ToastContext` (not in CLAUDE.md's `context/` list) and not `SocketContext` (keeps "connection" and "notification display" concerns separate).
- **Toast auto-dismiss raised from 4s to 8s** after live testing showed 4s wasn't enough time to read a toast while switching browser tabs mid-demo-rehearsal.
- **`SocketContext` stays a thin transport layer** — exposes the raw `socket` (or `null` pre-connect), no `joinChannel`/`leaveChannel` wrapper functions. One consumer today (`Channel.jsx`); wrapping now would be premature abstraction.
- **`scripts/seed.js` pulled forward from Phase 9 into Phase 3.** Multi-user local testing (mentions, room-scoping) has no path through the app's own UI — there's no join-team/invite endpoint in scope (see Phase 2's decision), so a second test account can never get onto an existing team through the product itself. Two options were considered: (a) build a `POST /teams/:id/join` endpoint, or (b) seed known demo users directly into the database. (a) was rejected — it's a 24th endpoint beyond CLAUDE.md's explicit ~23-endpoint list, real scope creep on a same-day deadline, and not something an interview demo would ever click through live anyway. (b) was chosen and doubles as real progress: CLAUDE.md's Phase 9 spec already names the exact 3 seed users (`employee@pagerslack.dev`/John/EMPLOYEE, `lead@pagerslack.dev`/Sarah/TEAM_LEAD, `manager@pagerslack.dev`/Mike/MANAGER) and team ("Engineering"), which Phase 7's escalation demo will need pre-existing role diversity for regardless — so this isn't a detour, it's the same work Phase 9 would have done, done early because Phase 3 needed it too.
- **`scripts/seed.js` is additive/idempotent, never destructive.** CLAUDE.md's literal seed-data wording ("Creates 3 users...one team...") reads as a from-scratch operation, but the user's own account already has a team named "Engineering" from manual Phase 1/2 testing (the exact name CLAUDE.md's seed spec also uses). A script that deletes-then-recreates a team called "Engineering" would silently wipe the user's real test data (channels, messages) on every run. Instead: the script finds "Engineering" if it exists and adds the 3 seed users onto it (upserting role/team, never deleting), creates it fresh only if missing, and only creates the `#general`/`#backend`/`#incidents` channels that don't already exist — any other channels (e.g. the `dev`/`qa` channels created during Sub-slice C testing) are left untouched. Safe to re-run any number of times.
- **`scripts/seed.js` cannot `require('mongoose')`/`require('bcryptjs')` directly**, despite both being installed. Node resolves bare `require()` specifiers by walking up from the *requiring file's own directory*, not by `process.cwd()` — `scripts/` (a sibling of `backend/`, not a descendant) has no `node_modules` of its own and neither does the repo root, so a direct import fails with `MODULE_NOT_FOUND` regardless of which directory the script is launched from. Fixed by only requiring files that live under `backend/src/` (which resolve their own dependencies fine, since `backend/node_modules` is an ancestor of those files) and reusing `authService.registerUser` for new-user creation instead of hashing passwords manually in the script — this also means the script exercises the exact same hashing path real registration does, rather than a parallel one that could drift.
- **`npm run seed` runs as `node ../scripts/seed.js` from `backend/`** (added to `backend/package.json`, not a new root script) — so `config/environment.js`'s `dotenv.config()` (which resolves `.env` relative to `process.cwd()`) finds `backend/.env` the same way `npm run dev` already does, with zero changes to `environment.js` itself.
- **Seed password (`password123`) is a known follow-up, not yet changed.** Chrome/Edge's built-in breached-password checker fires on it during login (`password123` is a top-of-list breached credential) — harmless functionally, but a distracting popup during a live interview demo. Flagged, not yet fixed as of this writing.
- **`SEED_PASSWORD` changed to `PagerSlack2026!`** (resolved the item directly above) — `authService.registerUser`'s internal `bcrypt.hash` call was extracted into an exported `hashPassword` function so `seed.js` could reset the password on *existing* seed users too, not just new ones (otherwise re-running the script after changing the constant would leave John/Sarah/Mike stuck on the old hash). Verified live: new password logs in (`200`), old one is rejected (`401`).

## Phase 4 — Incident creation

- **`assignedTo` deliberately not added to `Incident` yet** — same precedent as Phase 1 deferring `User.team` until the `Team` model existed: no consumer until Phase 5's `POST /incidents/:id/assign`, so adding it now would be a dead field.
- **No `sourceMessage` / "convert message to incident" link.** CLAUDE.md's endpoint list has no such field or action, despite the project's own narrative description ("turn messages into incidents"). Creation happens via a standalone "Create Incident" modal with a `channel` `<select>`, the same pattern the sidebar's create-channel form already uses — not a button hanging off a specific chat message.
- **`IncidentEvent.type` enum declares only `'CREATED'` for now**, not the full future set (`ASSIGNED`/`ACKNOWLEDGED`/`ESCALATED`/`RESOLVED`) — same precedent as `Notification.type` in Phase 3, which only declared `'MENTION'` and left room for Phase 7 to extend it. `actor` is a required `User` ref this phase; Phase 7's system-triggered `ESCALATED` events will need it to become nullable then, not now.
- **`generateIncidentNumber.js` is count-based (`INC-0001`) and has a real, accepted race condition** under concurrent creates — not fixed with a proper atomic counter/sequence, since at this demo's scale (one interviewer clicking one button at a time) the risk is theoretical, and building real concurrency safety for it would be effort spent on a problem this project will never actually hit.
- **`Modal.jsx` finally built** — deferred since Phase 1 for lack of a consumer; `CreateIncidentModal` is the first one.
- **`GET /incidents/:id/history` built this phase**, even though its only UI consumer (`IncidentTimeline`) doesn't exist until Phase 5 — cheap to add alongside the `IncidentEvent` write path it reads, and it's what let the `CREATED` event get `curl`-verified before any UI caught up to it.
- **Incidents page reached via a new nav link added directly in `Sidebar.jsx`**, not a new `Topbar.jsx` — same "no consumer yet" reasoning that deferred `Topbar` in Phase 2 still holds.
- **`utils/severity.js`** centralizes the `'LOW' → 'severity-low'` mapping from the `severity` enum to a `Badge` `variant` string, so `IncidentCard`/`IncidentDetails`/`CreateIncidentModal` share one place instead of each repeating `.toLowerCase()` inline.
- **No membership/team enforcement on `GET /incidents`** — returns all incidents, unfiltered, consistent with Phase 2's "no membership enforcement on reads" decision. Verified live: Sarah and Mike (seeded users) both see incidents John created.
- **`Modal.jsx`'s backdrop bug, found during live testing and fixed**: the backdrop `<div>` was nested *inside* the same wrapper `<div>` as the dialog instead of rendered as its sibling. Bootstrap's CSS gives `.modal-backdrop` a lower `z-index` (1050) than `.modal` (1055) — correct only when they're true siblings, which is how Bootstrap's own JS renders them. Nested the way it was, the backdrop (an explicitly `z-index`'d element) painted *above* the dialog content (which has no explicit `z-index` of its own), silently blocking every click and keystroke into the form while visually darkening it. Fixed by rendering the two as siblings in a fragment.
- **Title-required validation added as UX follow-up**, surfaced as a toast rather than an inline form error, per explicit request. Implemented by promoting `AppLayout`'s existing toast queue (built for Phase 3's mention notifications) into a general-purpose mechanism: `pushToast` extracted as a `useCallback`-memoized function and exposed through the same `Outlet` context that already carries `channels`, rather than building a second, parallel toast system for form validation. The mention-notification handler now calls the same `pushToast` internally — one queue, one render path, two callers.
- **Toast position moved from bottom-right to top-right**, applying to all toasts (mentions and form-validation alike) — a single `bottom-0` → `top-0` class change in `AppLayout.jsx`, since both toast types share the same stack/container.

## POC-scope reconciliation (`CLAUDE.md` rewrite → `Team.members`, register auto-join, ack/resolve ownership)

- **`CLAUDE.md` was rewritten mid-project to formalize what had already been decided piecemeal in conversation**: exactly one seeded team, deterministic one-user-per-role assignment, no invite/join flow, no team-creation UI. This was triggered by an externally-proposed team-invitation-system design that was rejected for the same reason the earlier join-team feature request was rejected — real RBAC/multi-tenancy scope a same-day POC doesn't need — but this time codified as policy instead of a one-off call.
- **`Team.members` array added** alongside the existing `User.team` back-reference. The two aren't reconciled into one source of truth (`User.team` still drives every existing membership read); `members` exists because the new `CLAUDE.md` describes access in terms of it ("anyone in `team.members`"), and it's kept in sync at registration and seed time. No new enforcement code reads it — access is trivially "everyone" by construction (one team, no second-team UI path), same as the Phase 2 decision this doesn't overturn.
- **Real bug found and fixed while wiring this up**: `authService.registerUser`'s initial retrofit used `Team.findOne()` with no filter to look up "the one team," which is only safe in a database that actually has exactly one team. This one has four (leftover `Engineering1`/`devv`/`sef` teams from manual Phase 1/2 UI testing, never cleaned up), so an unfiltered query non-deterministically returned whichever one Mongo listed first — a fresh registration would silently land on the wrong team. Fixed by querying `{ name: SEEDED_TEAM_NAME }`, a constant now shared between `authService.js` and `scripts/seed.js` (`backend/src/config/constants.js`) so the two can't drift. The stray teams themselves are left alone — deleting other data without being asked is out of scope for this fix.
- **Acknowledge/resolve authorization**: `incidentService.assertCanAct` allows the action if the actor is `incident.assignedTo`, OR if the actor's role outranks (or matches) the incident's current `escalationLevel` (`EMPLOYEE < TEAM_LEAD < MANAGER`). Deliberately keyed off `escalationLevel`, not `assignedTo`'s role — an `EMPLOYEE`-level incident stays actionable by any `EMPLOYEE` even after being manually reassigned to a `TEAM_LEAD`, since manual assignment doesn't change the escalation level. This matches a literal reading of the rule as written, not a stricter interpretation, and was verified live (403 for a non-assignee `EMPLOYEE` against a `TEAM_LEAD`-level incident, 200 for a non-assignee `MANAGER` against the same incident).

## Future scope (out of bounds for this POC, noted for a real version)

Positions this project's boundaries as deliberate, not unfinished — each item below was proposed at least once during the build and declined for the same underlying reason: this is a same-day demo of the communication + incident-lifecycle story, not a multi-tenant product.

- **Invite/join flow.** A real product needs `POST /teams/:id/invite` + accept/decline, per-user pending-invitation state, and a `TeamMember`-style join table instead of a flat `members` array. Proposed twice (a lightweight "join a team" feature, then a full invitation-system design with role-permission matrices) and declined both times — this POC seeds exactly one team with exactly 3 role-diverse users specifically so the collaboration demo never needs a join flow to work.
- **Dynamic, multi-user-per-role escalation targeting.** The escalation worker's `User.findOne({role: nextLevel})` assumes exactly one user per role — real on-call needs schedules, rotations, and a way to pick among several `TEAM_LEAD`s. Fine for a demo where "Sarah is the team lead" is a fixed, known fact; would break the moment a second `TEAM_LEAD` existed, which is exactly why registration hard-codes new users to `EMPLOYEE`.
- **Real channel-membership model.** Access is currently "everyone on the one team, for every channel that team owns" — no private channels, no per-channel membership. A real version would need a join table and permission checks per channel, not just per team.
- **`priority` as a field distinct from `severity`.** Proposed twice in different external designs; declined both times as redundant surface area with no behavioral effect in this codebase — `severity` already answers the question a `priority` field would ask again.
- **Complex RBAC beyond the two-case ack/resolve rule above.** A real permission matrix (who can create channels, delete messages, reassign across teams, etc.) is real product surface area this POC's single-team, single-role-set assumption doesn't need.

## Phase 7 — Automatic escalation

- **`Incident.levelChangedAt` added as a dedicated escalation clock**, not a reuse of `updatedAt`. `updatedAt` is bumped by unrelated saves (e.g. manual reassignment via `assignIncident`), which would silently reset the escalation window every time someone assigns an incident if used as the trigger. `levelChangedAt` is touched only at creation and inside `escalateIncident` itself.
- **`IncidentEvent.actor` relaxed from required to optional** — `ESCALATED` events are system-triggered, no human actor exists to record. Flagged as a known future need back in the Phase 4 entry above; this is that moment. Every other event type still always passes a real actor in practice.
- **Escalation emits to both the incident's `channel:<id>` room and the new assignee's own `user:<id>` room** (`emitIncidentEventToUser`, new alongside the existing `emitIncidentEvent`). `CLAUDE.md`'s socket-room rule literally says the user room receives "all `incident:*` events for that user" — Phase 5's `assign`/`acknowledge`/`resolve` only ever emit to the channel room, a real, accepted gap not retrofitted here (out of scope for already-committed code). Escalation is the one event where the user-room delivery is the actual feature: the newly-responsible person needs to be notified even if they're not sitting in that channel. `AppLayout.jsx` picks it up with one more `socket.on('incident:escalated', ...)` listener, reusing the existing `pushToast` — no new Notification-model changes, since that schema is mention-shaped (`fromUser`/`message` required) and not a fit for a system-triggered event.
- **Worker guards against overlapping ticks** with a simple `running` boolean, since `setInterval` doesn't wait for the previous async callback to finish.
- **`ESCALATION_POLL_INTERVAL_MS`/`ESCALATION_ACK_WINDOW_MS` are optional env vars** (default 5000/15000, matching the demo spec), not added to `environment.js`'s required-at-boot list — same precedent as JWT expiry being hardcoded rather than required. Verified live with a 2s/3s override: an unacknowledged incident escalated EMPLOYEE→TEAM_LEAD→MANAGER correctly, stopped permanently the instant it was acknowledged (even well before the window elapsed), and never escalated past MANAGER.

### Auto-assign-to-employee (added after initial Phase 7 verification)

- **Every incident routes through the seeded `EMPLOYEE` (John) before the escalation ladder ever starts, regardless of who reported it.** If John reports it, it self-assigns to him immediately at creation (`incidentService.createIncident` checks the reporter's role) — no timer, nothing to wait for. If a `TEAM_LEAD`/`MANAGER` reports it, it's created unassigned; the reporter can manually assign it to John within `AUTO_ASSIGN_WINDOW_MS` (default 10s), or `escalationService.runAutoAssignSweep` (run at the start of every worker tick, before the escalation sweep) auto-assigns it to him — an `AUTO_ASSIGNED` `IncidentEvent` (`actor: null`, system-triggered, same pattern as `ESCALATED`), an `@John` channel message, and `incident:updated` emitted.
- **The toast to John needed no new plumbing.** The auto-assign channel message contains a real `@John` mention, which transparently reuses the Phase 3 mention pipeline exactly like manual assignment already does — no new `AppLayout` socket listener, no `Notification` schema changes.
- **`levelChangedAt` now also resets on an incident's first assignment** (auto or manual) while still at `EMPLOYEE` level, not just at creation and on escalation. Without this, a lead/manager-created incident that sat unassigned for the full 10s auto-assign window would only leave John 5 of his 15 seconds (15 − 10) before escalating out from under him — the clock needs to start when he actually has it, not when it was reported. This does **not** apply to reassignment at an already-escalated level (e.g., handing a `TEAM_LEAD`-level incident to a different assignee) — that still doesn't reset the clock, preserving the original anti-gaming protection from the base Phase 7 design.
- **Second real bug, same root cause as the `Team.findOne()` one**: `User.findOne({ role: 'EMPLOYEE' })` is fundamentally unsafe, not just unsafe-today — every self-registration creates another `EMPLOYEE`, so that role can never be assumed unique the way `TEAM_LEAD`/`MANAGER` currently are by construction. In this dev database specifically there were already 12 `EMPLOYEE`-role accounts from manual testing; the auto-assign sweep's first live run grabbed an arbitrary one of them (not John) because of this. Fixed by adding `SEEDED_USER_EMAILS` to `backend/src/config/constants.js` and switching **all three** seeded-user lookups (auto-assign's `EMPLOYEE`, and escalation's `TEAM_LEAD`/`MANAGER` lookups too, for consistency even though those two are still safe today) to match by exact seeded email instead of bare role. Re-verified live after the fix: auto-assign correctly targets John every time.
- **New registrations are deliberately invisible to auto-assign/escalation, but not to acknowledge/resolve.** Because the seeded-email fix above targets John specifically, a freshly self-registered `EMPLOYEE` will never be auto-assigned an incident or reassigned into the escalation chain. But `assertCanAct`'s rule ("assignee, or role rank ≥ escalation level") means any `EMPLOYEE` — including a brand-new registration — can still acknowledge/resolve an `EMPLOYEE`-level incident, since a fresh incident starts at that level and every `EMPLOYEE` outranks-or-equals it. This is read as a straightforward consequence of the existing rule as written, not tightened to "must literally be John," since `CLAUDE.md` never restricted it to a specific identity.

### Known issue — `IncidentEvent` history lost for 12 pre-existing incidents

While verifying the fixes above, a throwaway cleanup script ran `IncidentEvent.deleteMany({})` with an empty (unscoped) filter, wiping the entire collection instead of the one test document it was meant to remove. All timeline history for the 12 incidents created during earlier manual testing (`INC-0001` through `INC-0012`) is gone — the `Incident` documents themselves are untouched, only their `IncidentEvent` rows. Not recoverable via anything available here: MongoDB Atlas's free M0 tier has no continuous backups or point-in-time recovery. A partial fix is possible — each `Incident` still has its own `createdBy`/`createdAt`, so a single reconstructed `CREATED` event per incident could be backfilled — but not the specific who/when of any acknowledge/resolve action, since that only ever existed in the deleted rows. Offered to the user, not yet actioned as of this writing.
